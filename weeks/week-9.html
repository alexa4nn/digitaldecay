Week 9: Prototype Development — Publishing the Archive

Overview

Today we will spend more time building rather than theorizing, but before you can build, you need somewhere for your work to live publicly. We start with a hands-on demo of how to push a site to the web using GitHub Pages, both from the terminal and from VS Code, and look at an alternative host (statichost.eu) for anyone who wants something outside the Microsoft/GitHub ecosystem. Then we'll get your 3D scans (now exported as proper .glb files) into the shared class drive so they can be integrated into the group index. The rest of the time spent in class is for building, with a mid-session group critique to test how your archive is reading.

Demo: Deploying to GitHub Pages from the Terminal

The terminal route is bare bones, but is the more durable skill. Once you understand it, every other deployment tool makes sense. We will walk through this together.

First, you will want to create a github account if you haven't already. then you will want to create a new repository. You can select MIT License if you would like to add a copyright. But it is not required.

The basic flow:

git init
git add .
git commit -m "first commit"
git branch -M main
git remote add origin https://github.com/your-username/your-archive.git
git push -u origin main

Then go to your repo on github.com, click Settings → Pages, and set the source to main branch, root folder. Your site will be live at https://your-username.github.io/your-archive/ within a minute or two.

A few things to watch for:

  • file paths must be relative (images/scan.glb, not /Users/you/Desktop/...)
  • file names are case-sensitive on GitHub Pages but not on your Mac. This is the #1 reason a site works locally and breaks online
  • the main entry file must be named index.html

Demo: Deploying to GitHub Pages from VS Code

If the terminal feels like too much right now, VS Code can do almost the same thing through its built-in Source Control panel and the GitHub extension. We will walk through:

  • signing into GitHub from inside VS Code
  • using "Publish to GitHub" to create the repo in one click
  • committing and pushing changes through the Source Control sidebar
  • enabling Pages in the browser the same way as above

Both routes end in the same place. Pick the one that you'll actually keep using.

Alternative: statichost.eu (zip upload, no git)

For students who don't want to deal with GitHub auth today, or who want a non-American, GDPR-compliant host on principle, statichost.eu is a Sweden-based static host. The free tier gives you 10 GB of traffic and 100 build minutes per month, which is more than enough for an archive site.

Statichost can pull from a git repo like GitHub Pages does, but it also has a direct zip upload option that skips git entirely. This is the path to take if you're stuck on 2FA or PAT setup and just need a URL.

Zip upload workflow:

  • Make an account at statichost.eu
  • Click Add site → upload zip file
  • Zip the contents of your site folder (not the folder itself, or all your files will end up under /public/)
  • Upload. You get a URL at your-site.statichost.eu
  • To update the site later, zip the new version and re-upload from the dashboard

The tradeoff: no version history, no record of changes, and you have to re-zip and re-upload every time you edit. For a one-week sprint to get a site live, that's fine. For ongoing iteration, git is better.

Why you might stick with GitHub Pages:

  • everyone in the class will be using it, so troubleshooting is easier
  • you get version history, which is itself a kind of archive
  • updates are one command instead of a re-zip and re-upload

Why you might choose statichost (beyond just dodging GitHub auth):

  • the servers are in Europe, the company is European, and no personal data is logged
  • it fits the themes of the course. Different infrastructures preserve, surveil, and remember differently
  • it is a small platform and small platforms disappear. Using one is itself an archival gesture

Exercise: Upload Your .glb to the Class Drive

By now you should have your 3D scan back from your scanning app. Today we make sure everyone has a properly-exported .glb file (not .obj, not .ply, not a link to a Luma viewer page) sitting in the shared class drive folder, named lastname-firstname.glb.

A quick note on the scanning app: if Luma AI worked for you, great. Keep using it. If you ran into export issues or you're on Android, KIRI Engine is the alternative we'll demo. It is free, cross-platform (iOS and Android), and exports cleanly to GLTF/GLB on the free tier (3 free exports per week, which is plenty). The capture process is nearly identical: walk around the object, upload, wait, download. The difference is where the file lands afterwards.

Steps:

  • Open your scan in Luma AI or KIRI Engine.
  • Export as .glb (not .obj, not .usdz). If your app gives you a poly-count choice, go low or medium. These files need to load in a browser.
  • Rename the file lastname-firstname.glb.
  • Drop it in the shared class drive folder (link in the class slack).
  • Drop the same file into your own site's models/ or assets/ folder and link to it from your landing page with <model-viewer>.

If your scan has holes, warped surfaces, or floating geometry, keep it. Don't try to fix it. That's the point.

Work Block 1 (45 minutes)

Studio time. Get your site live somewhere, even if it's just a landing page with your 3D object on it. The goal for this block is a working URL you can share with another student, not a finished site. Push early, push broken, push often.

Group Critique (30 minutes)

Break into groups of three. Each person gets ~10 minutes. Open your live site in the browser and walk the others through:

  • what your archive is about
  • where absence shows up in the interface so far
  • one thing you are stuck on

The other two should ask: does the design carry the concept? Where do you want to look that the site is not letting you look? What is the site doing that surprises you, for better or worse?

Work Block 2 (45 minutes)

Back to building. Use what came up in critique. By the end of class today you should have:

  • a published URL
  • your 3D scan visible on the landing page
  • at least one archive item rendered with its metadata (including any uncertainty/ghost fields)

Questions + Troubleshooting (last 15 minutes)

Open floor. Bring problems you hit during work blocks: git errors, model-viewer not rendering, CORS issues with the .glb, layout breaking on mobile, anything.

Assignment

Keep building. Next week is final presentations. By Week 10 your site needs:

  • a working published URL
  • the 3D object on the landing page as the entry point
  • the archive index with all items, including ghost entries
  • at least one individual record view
  • a clear visual identity

Submit your URL to the shared drive by the night before Week 10 so the group index page can be assembled.
